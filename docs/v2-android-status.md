# Android schema-v2 status (P3-12, P3-12b, P3-12c, P3-12d, P3-19, P3-21, P5-06)

This doc describes the native v2 Android app: the screens read the bundled v2 SQLite store through
domain repositories, and every write is a typed P3-14 catalog command sent through the command
outbox. The iOS equivalent is `avago/docs/v2-ios-status.md` (P3-11).

- Enablement and reset: `docs/v2-reset-spec.md`.
- Contract (AvagoSvc): `schema/contract/design/sync-wire.md`, `out/openapi/sync.yaml`,
  `out/sqlite/*.sql` and `out/commands/catalog.json`. Notes: `schema/v2/notes/p3-07.md`,
  `p3-08.md`, `p3-14.md`, `p3-14c.md` (the per-item map of the mobile gap catalog: command,
  L38 REST online action or projection for every P3-12c removal) and `p3-18.md` (the resolution of
  the P3-12d catalog requests, implemented here by P3-19).
- The DDL, the catalog and the permission keys are generated by `scripts/gen_v2_contract.py` from
  AvagoSvc `origin/schema-v2` at `acd4207` (see `V2GeneratedSchema.SOURCE_REVISION`; unchanged since `b8616bc` apart from the revision): 180
  commands (P3-14, P3-14b rentals, P3-14c gap catalog, P3-18 fields), 154 projections. P3-18 added
  the `cost_line_id` attachment target, cost-line identity (GTIN, country of origin and the other
  `part_snapshot` keys), the `activity_id` document owner and more clearable fields, and made
  `customer_ledger_entries.card_last4`, `rental_billing_cycles`, `account_preferences` and the
  closed `asset_status_intervals` (365-day history window) mobile. The `worker_rates` mobile key
  now includes `valid_during_start`. `72faf96` applies QR label templates (no DDL change; the
  synced read-only `label_templates` projection already carries them).
- P3-15b (L37) replaced the `sync_nudge` push with the E13 silent hint
  `{"t":"sync_hint","account_id":…,"w":…}`; `AvagoFcmService` starts one pull + flush for it.

P3-12b's legacy bridge (Room read mirror plus REST write shim) was removed in P3-12c. Nothing reads
legacy Room tables for business data, and nothing writes business data over REST.

## 1. Enablement

The v2 store is used when `V2Flag.isEnabled()` is true **and** the legacy reset marker is complete
(`V2StoreGate`).

- **Internal builds.** Build with `-Pv2Default=true` (`BuildConfig.V2_DEFAULT` →
  `V2Flag(defaultEnabled = true)`).
- **Debug override.** Settings → debug v2 toggle (M-02).
- **Flag off.** With the flag off the app is inert by design: per U5/U6 there are no external users
  and cutover is fresh, so the legacy sync path was deleted rather than kept alive. `SyncEngine`
  is a no-op, `SyncGate` stays closed, and the repositories emit empty lists while
  `V2ActiveStores` holds no store.

## 2. Native architecture

```
Compose screen ─► ViewModel ─► domain repository interface   (core:data domain/*)
                                   │
                                   ▼
                        V2*Repository (core:data v2/repo)
              reads: SQL over the v2 store + V2OverlayMerge  ─► Flow<domain model>
              writes: command builder (v2/commands) ─► V2CommandService.submit
                                   │
                                   ▼
   V2CommandOutbox: pending_commands + optimistic overlay + upload_jobs, in one transaction
                                   │  flush (V2FlushScheduler / SyncEngine)
                                   ▼
   E12 upload (V2ApiUploader: register → PUT → finalize) ─► POST /v2/…/commands
   committed → acknowledged → retired once a sync covers result_watermark (overlay dropped)
   rejected  → overlay deleted (rollback); FailedChange shown on the Failed changes screen
```

### Reads

Each repository runs SQL against the v2 store (`V2StoreAccess`) and re-queries when a table it
reads changes (table-level change notifications), so it returns a `Flow` of domain models.

Pending optimistic changes are merged by `V2OverlayMerge`, which handles:
- upserts, including explicit null clears;
- creates and deletes;
- additive deltas, such as stock quantities and purchase-order totals;
- re-checking the query filter after a row changes.

Money and quantities are converted from micros and minor units (`V2Micros`, `V2Money`) only at
this boundary.

### Writes

- **Payload types.** `scripts/gen_v2_contract.py` generates `V2GeneratedCommands.kt` from
  `catalog.json`. It contains typed payload classes for all 180 commands (192 classes with the
  nested payload types), each with its operation name and a `Clear` enum listing the fields that
  can be cleared. Keyless commands (natural-key upserts such as `stock.stocking_policies.set`)
  carry no entity key and no base version. `V2GeneratedPermissions.kt` lists the permission keys.
- **Builders.** The builders are `StockCommands`, `InventoryCommands`, `PurchasingCommands`,
  `WorkOrderCommands`, `MaintCommands`, `PmCommands`, `AdminCommands`, `PreferenceCommands`,
  `CoreCommands`, `RentalCommands` and `RentalAccountCommands`. Each builder:
  - validates the domain rules (for example, a PO can be approved only while it is pending approval);
  - computes the `set`/`clear` diff against the stored row with `V2UpdateDiff`;
  - sets `base_version`;
  - builds the optimistic overlay patch.
- **Clearing fields.** A field emptied in a form is sent in `clear` and overlaid as `NULL`.
  If the field's command has no `Clear` entry for it, the builder throws
  `FieldNotClearableException` and the form shows the error. It is not silently ignored.
- **Unchanged forms.** An edit that changes nothing returns no command.
- **Submit.** `V2CommandService.submit` enqueues the command, its overlay, its dependency edges
  and its upload jobs in one transaction, then schedules a flush.

### Outbox

| Topic | Behaviour |
|---|---|
| Ids | UUIDv7 ids (L32), which double as idempotency keys; `request_hash` |
| Ordering | causal order; per-entity ordering |
| Gating | dependency gate and upload gate |
| Retries | receipt reconciliation for unknown outcomes; capped backoff and `Retry-After` |
| Upgrade | 426 → update-required screen |

**On rejection:**
- The overlay is deleted, which is the rollback: the screen shows the server row again
  (a `version_conflict` keeps the rolled-back overlay for "apply mine", below).
- Dependent commands are rejected with `dependency_rejected`.
- The failure (operation, entity, code, message) appears in **Settings → Failed changes**
  (`FailedChangesScreen`), where it can be dismissed.

**Per-record sync state.** Detail screens show it via `observeRecordState`.

**Conflicts.**
- A `version_conflict` rejection carries its `conflict_id`. It is listed with the failed changes,
  and the server row stays authoritative until the user decides.
- Open `sync_conflicts` rows (from this or another device) are listed in **Failed changes** with a
  per-field diff (yours vs server, `ConflictDiff`). They are settled with
  `sync.sync_conflicts.resolve`:
  - **apply mine:** the refused edit is re-queued on the record's current version with its
    rolled-back overlay, and the resolve depends on it;
  - **keep server:** resolve only;
  - **dismiss.**
- Open conflicts are read with the overlay applied, so a resolve hides them at once.
- Form-level: log edits whose entry changed while the form was open are three-way rebased
  (`LogRebase`); overlapping changes open a keep-mine/reload dialog.

### Uploads (binaries)

1. `V2FileStager` copies a picked or captured file into app storage under its UUIDv7 `file_id`.
   That copy also serves local display.
2. The link command (`maint.attachments.create`, `core.documents.create`, etc.) is enqueued
   together with an `upload_jobs` row.
3. The upload gate holds the command until `V2ApiUploader` has completed E12 register → PUT
   (`V2HttpBlobTransport`, presigned URL) → finalize.

### Sync

- **`V2SyncEngine`** handles:
  - sessions and paging, with each page applied atomically together with its cursor;
  - tombstones and the version guard;
  - FK carry-over;
  - acks and 426.
- **`V2SyncCoordinator`** handles:
  - device registration;
  - opening and publishing the stores;
  - pull, then outbox flush.
- **`SyncEngine`** (core:sync) is a thin facade over the coordinator, used for sync/resync, rate
  limiting and account-gone events.
- **`SyncWorker`** runs periodically and on connectivity, foreground and FCM nudges.
- **`SyncGate`** opens from the v2 store's bootstrap state.

The sync-engine details are unchanged from P3-12 (see git history of this file).

### Added in P3-21 (P3-20, P4-01b)

- **Typed uploads (P3-20).** Storage checks the bytes against the registered type.
  - `V2FileStager` sniffs the first KiB (`V2MediaType`, the server's `media.rs` signatures) and
    registers the sniffed type, falling back to the declared one; chat media are sniffed the same
    way.
  - The REST photo registrations (crew asset and loan photos, provider job photos) send
    `content_type: image/jpeg` (the app JPEG-encodes them) and PUT with the same type.
  - `400 unsupported_media_type` at E12 register and `415 unsupported_media_type` /
    `media_type_mismatch` at the PUT throw `V2UploadRefusedException`. The outbox rejects the
    command with that code (no retry), and Failed changes explains it in the user's language.
    REST uploads surface the server code (`JsonApi.upload` parses the error body); the crew and
    provider screens show a localized message.
  - The unused legacy photo upload (`AvagoServiceClient.getPhotoUploadUrl`/`uploadPhotoBinary`,
    which registered no type) is removed.
- **Typed 403s (P4-01b).** `membership_suspended`, `membership_inactive`, `user_suspended` and
  `user_deactivated` are read from REST (`code`) and `/v2` (`error`) bodies.
  - The authenticated client reports them (`AccessDenialReporter`, skipping `/auth/` routes) to
    `AccessDenialMonitor`, keyed to the active account. A membership denial for another account
    is ignored; a user denial always applies.
  - `V2SyncEngine` returns `AccessDenied(code)` for any `403` on a sync route (`/v2` still answers
    an inactive membership with generic `forbidden`; see the P3-21 server request). The outbox
    keeps a command refused with a typed `403` unsent (no attempt counted) and stops the flush.
  - While the active account is denied, `V2SyncCoordinator` skips pull and flush, `SyncWorker`
    completes without a retry, and Scout's pending drain stands down. Nothing is dropped.
  - `AccessDeniedDialog` (non-dismissable, over every non-auth screen) explains the denial:
    **Try again** clears it and syncs; **Switch workspace** (membership denials) opens the account
    switcher; **Sign out** signs out of the workspace, or of every account of a denied user.
    Sign-in, account switch and sign-out clear it. The sign-in screens show the same localized
    messages for a typed `403`.
- **REST parity items of P3-20** (cost-line part identity, tech-profile clears) do not apply: the
  app writes both through v2 commands (§3, "Added in P3-19").

### Added in P5-06 (plan 4.1, 4.2, 4.3, 6.4, 13.6)

The generated contract now follows AvagoSvc `origin/schema-v2` `73502d2` (P5-04,
`V2GeneratedSchema.SOURCE_REVISION`), following the adoption steps in `schema/v2/notes/p5-04.md`.

- **In-place v1 → v2 upgrade (plan 6.4, L43).**
  - `migrations/{business,chat}/v001_to_v002.sql` and `migrations/manifest.json` are embedded as
    core:data resources. The generator checks their SHA-256 against the manifest.
  - `V2Database.open` runs every step from the file's `user_version` up to
    `V2_DB_SCHEMA_VERSION` (2), with foreign keys off, in one transaction. It requires an empty
    `PRAGMA foreign_key_check` and `user_version` = 2, then writes the new DDL hash and projection
    versions to `v2_client_meta`. There is no rebuild and no re-bootstrap: the cursor, the outbox
    and the device registration are kept.
  - A store from a newer build (`V2StoreTooNewException`) and a failed upgrade
    (`V2MigrationException`) are never deleted; the open fails and the file is kept. Only a file
    owned by another user or account is still rebuilt (L12).
  - The 26 manifest `retired_tables` have no mobile table (`mobileTable = null`); their
    projections stay wire entities.
- **SQLite with the WAL-reset fix (plan 4.2).** `androidx.sqlite:sqlite-bundled` 2.8.0-alpha04
  bundles SQLite 3.53.4 on every ABI and API level; the framework SQLite is never used. On every
  open, `V2SqliteRuntime.check` requires at least 3.51.3, or one of the upstream backports 3.50.7
  or 3.44.6, and refuses any other runtime. JVM tests use `sqlite-jdbc` 3.53.4.0.
- **Chat file per user and account (plan 4.1, L42).**
  - Chat now lives in `accounts/<account>/<user>/v2/chat-<user>-<account>.sqlite`: the contract chat
    tables, the contract `outbox` (carried across rebuilds) and the client-only `chat_client_cache`
    (`ChatCache`: one JSON document per thread, message, mention, roster entry and member, refilled
    from REST). The Room `ChatDatabase` (`chat.db`) is removed. The retired device-wide
    `chat.db` and `rentalops.db`, with their sidecars, are deleted when the stores open
    (`V2StorePaths.prepareStoreFiles`). Unsent rows of the old Room outbox are not migrated (the
    plan's reset rule); the cache resyncs from REST.
  - Sends, replies, edits and deletes go through `ChatOutboxQueue` in causal order:
    - the head row is leased;
    - a send carries its outbox id as `client_ref`, so an ambiguous failure is re-sent without
      creating a duplicate;
    - transport, 5xx, 408 and 429 errors retry the head with backoff (2 s doubling, up to 30 s);
      after 5 attempts the message shows as failed but stays queued;
    - a 401 or another 4xx is rejected, which undoes the optimistic edit or delete or marks the
      send failed;
    - an edit or delete of a send that has not gone out yet rewrites or drops the queued send;
    - the server echo replaces the optimistic message.

    `OutboxRetryCoordinator` drains each account under a mutex, and the work is woken on
    connectivity, a periodic flush and the next due attempt.
  - Chat projections are applied to the chat store before the business page and its cursor
    commit (unchanged; plan 12).
- **Rental field operations folded into `:feature:rentals` (plan 4.1).**
  - The `:feature:rentalsops` module is now `com.avago.feature.rentals.ops`
    (`feature/rentals/OPERATIONS.md`) and keeps every screen, route, push event and
    permission gate.
  - Its data already lived in the typed business tables (`rental_delivery_tasks`,
    `rental_transfers`, …). Its own `rentalops.db` is deleted.
  - Route pings queue in `accounts/<account>/route_pings.json`.
- **Pending-media eviction (plan 4.3).**
  - `V2StagedMedia`: a staged copy is the only copy of an unsent photo, signature or document,
    so it is never evicted.
  - `V2OnlineUploads` and `V2ApiUploader` mark a copy as uploaded once it is finalized
    (`.uploaded/<file id>`). `trimCache` (`V2FileCache`) then deletes uploaded copies, oldest
    first, down to the budget. Those files stay readable through `files/{id}/download`.
- **At-rest protection (plan 13.6).**
  - Account stores, staged uploads (`v2files/`), captured rental photos and generated PDF reports
    stay in credential-encrypted internal storage.
  - `data_extraction_rules.xml` excludes them, and the encrypted credentials, from cloud backup
    and device transfer. `backup_rules.xml` stays an allow-list of plain preferences.
  - No component is direct-boot aware. `StoreAtRestConfigTest` checks all three rules.
- **Chat media follows the server contract (P5-05, AvagoSvc `a6e8a39`/`81fa0f1`).**
  - `POST /chat/media/presign` answers `upload_url`, `storage_key`, `cdn_url`, `max_bytes` and
    `content_type`. The client used to expect `media_url`/`expires_at`, which the server never
    sent, so every photo, document and voice-note send failed before upload.
  - After the PUT, a message references the upload by its storage key: an image as
    `{api}/chat/media/{storage_key}` in `image_urls`, a voice note as `audio_key` and a document as
    `attachment_keys` (`ChatSendPayload`, queued through the ordered outbox). An attachment-only
    message has an empty body.
  - Synced messages map `image_keys`, `audio_key` and `attachment_keys` to the same
    `/chat/media/{key}` URLs, so the echo of a send shows its media once.
  - `/chat/media/{key}` needs the bearer token and redirects to a short-lived signed URL.
    `AvagoServiceClient.signedChatMediaUrl` reads the redirect without following it; the signed
    URL is then fetched without the bearer. Coil loads chat images through `ChatMediaFetcher`;
    voice notes and documents are signed (`ChatMediaAccess`) just before playback or opening.
- **Rate card and tax rate writes:** none on Android (rate cards and tiers are read-only,
  `tax_rates` is retired, and there is no shop-import commit), so the P5-02 `409
  rate_period_overlap` error cannot reach the app.
